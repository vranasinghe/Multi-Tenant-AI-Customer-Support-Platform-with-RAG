# Phase 5 — Conversation engine

Current provider transport hardening (AUD-03): configured chat and embedding endpoints share
startup URL validation. HTTPS with certificate verification is the default; staging/production
always require it. All redirects are rejected and proxy/certificate environment variables are
not inherited by provider clients. For the tightly restricted local HTTP exception and migration
steps, see DEVELOPMENT.md section 9. No paid provider is configured by this change.

Implemented against the pasted development guide's Phase 5. This is **Phase 3** in the repository roadmap. The existing application's architecture and permissions remain the authority.

## Run the offline demonstration

Prerequisites: Docker Desktop, the repository's pinned Node/pnpm versions, dependencies installed, and `.env` created from `.env.example` (see DEVELOPMENT.md). Keep existing database passwords when reusing a local database volume.

In PowerShell at the repository root:

```powershell
$env:LLM_PROVIDER='demo'
docker compose up -d --build --wait
```

This applies migration `0005` and starts the API, dashboard, Postgres/pgvector, Redis, worker, object storage and Mailpit. `demo` is an explicit offline transport fixture. Its canned response is **not generated by an AI model**. It is refused in production.

1. Open http://localhost:3000 and create an account and organization.
2. Open http://localhost:8025 and follow the verification link in the local email.
3. Create a chatbot. Under Knowledge, upload a TXT file containing: `Returns are allowed within thirty days of delivery. Returned items must be unused and in original packaging.` Wait for **Ready**.
4. Open the chatbot's **Test chat** tab. Ask `What is the returns policy?` The fixture streams a clearly labelled demo answer and source `[1]`.
5. Mark it Helpful, reload, and reopen Test chat. The persisted reply and feedback return.
6. Start a New conversation and ask `Explain astrophysics quasars galaxies?` The relevance gate should return the configured fallback without a generation call.

Run the automated demonstration (creates throwaway local users/content):

```powershell
pnpm --filter @acs/web exec playwright test e2e/chat.spec.ts
```

## Configure a real provider

Set these server-only values in `.env` and remove the shell's demo override before recreating the API:

```dotenv
LLM_PROVIDER=openai_compatible
LLM_BASE_URL=https://your-provider.example/v1
LLM_API_KEY=your-private-provider-key
EMBEDDING_PROVIDER=openai_compatible
EMBEDDING_MODEL=your-1536-dimensional-embedding-model
EMBEDDING_API_KEY=your-private-embedding-key
```

```powershell
Remove-Item Env:LLM_PROVIDER -ErrorAction SilentlyContinue
docker compose up -d --force-recreate api worker beat
```

Choose an existing allowlisted chatbot model (`app/services/chatbots/registry.py`) that the endpoint supports. Chat uses the compatible `POST /chat/completions` streaming contract, including optional usage events. It passes `max_tokens`, `temperature` and `stream_options.include_usage`. Providers must support that contract. Redirects are disabled; keys never reach browser code. Reindex existing documents after changing embedding models. Recalibrate `CHAT_MIN_VECTOR_SCORE` with your real embedding model and customer questions; `0.15` is a development starting point, not a measured production threshold. The existing hash embedder has no semantic knowledge.

Update `CHAT_MODEL_PRICES` for your provider. Values are operator-maintained **estimates per million input/output tokens**, not live prices or invoices. No paid model calls are needed for automated tests. Production answer quality and provider-specific compatibility require a real-provider evaluation before release.

## API actually shipped

Dashboard routes use the existing session cookie, membership lookup and CSRF header `X-Requested-With: platform`. Every organization-scoped route declares one permission. IDs in request paths are checked server-side.

- `POST /api/v1/orgs/{org}/chatbots/{bot}/conversations` — create a playground conversation (`chatbot:test`, verified email).
- `GET /api/v1/orgs/{org}/chatbots/{bot}/conversations` — latest 50 conversation summaries (`conversation:read`).
- `GET /api/v1/orgs/{org}/conversations` — org inbox with search, filters and cursor pagination (`conversation:read`).
- `GET /api/v1/orgs/{org}/conversations/{conversation}` — transcript, status, CSAT, handoff and events (`conversation:read`).
- `GET /api/v1/orgs/{org}/analytics/summary` — live product metrics from stored events (`analytics:read`). See [analytics-metrics.md](analytics-metrics.md).
- `GET /api/v1/orgs/{org}/conversations/{conversation}/messages?cursor&limit` — earlier transcript pages (`conversation:read`, `limit` ≤ 100, default 50): `data` oldest first, `next_cursor` leads further back. The transcript response returns the newest 200 messages and sets `older_cursor` when there are more. Cursors name their organization, list and filters; anything else is `400 invalid_cursor`. They grant nothing. Lists are not snapshots: new activity moves a conversation to the top.
- `POST /api/v1/orgs/{org}/conversations/{conversation}/messages` — SSE (`chatbot:test`). Body: `{"content":"Returns policy?","context_messages":12}`. Clients cannot supply roles, history, tenant IDs or model overrides.
- `PUT /api/v1/orgs/{org}/conversations/{conversation}/messages/{message}/feedback` — `{"rating":1}`, `-1`, or `0` to clear (`chatbot:test`). Only finished assistant replies accept feedback.
- `POST /api/v1/orgs/{org}/chatbots/{bot}/widget-sessions` — issue a restricted session (`channel:manage`, verified email). Requires an active bot. Returns `token`, `conversation_id`, `expires_at` once. Send `Cache-Control: no-store` when forwarding this credential from your own trusted backend; do not embed it in static source or URLs.

Restricted public transport uses **only** `Authorization: Bearer <token>`:

- `POST /public/v1/chat/messages` — same bounded message body and SSE protocol; conversation is taken from the credential.
- `GET /public/v1/chat` — only this session's transcript, in the public shape (WIDGET_DEPLOYMENT.md).
- `PUT /public/v1/chat/messages/{message}/feedback` — only this session's completed assistant messages.

Tokens cannot authorize dashboard APIs. Dashboard cookies cannot authorize public transport. Tokens are random 256-bit secrets, stored only as SHA-256 hashes, expire after 15 minutes by default, and are bound to one org/bot/conversation and the bot's current public key. Key rotation, pausing/deleting a bot, or restricting/deleting an organization prevents further public use. Public keys alone cannot mint sessions. There is deliberately no anonymous session issuance endpoint until Phase 6 implements domain controls and widget onboarding. Current CORS allowlists still apply to browsers; Origin is not authentication. Add only your trusted widget frontend origin to `CORS_ALLOWED_ORIGINS` when integrating that frontend.

## SSE contract

POST using `fetch()` and a streaming reader, not EventSource. Events contain JSON `data:` frames:

```text
event: meta
data: {"conversation_id":"...","message_id":"..."}

event: delta
data: {"text":"Returns are allowed..."}

event: done
data: {"id":"...","role":"assistant","content":"...","status":"complete","citations":[],"input_tokens":120,"output_tokens":25,"estimated_cost_usd":"0.000088","usage_estimated":false,"error_code":null,"feedback":null}

```

The final `done` object is authoritative. Citations are included there rather than a separate citations event. Mid-stream failures emit `error` followed by `done` with `status=failed`; pre-stream authorization, quota and setup failures return Problem Details with a normal HTTP error. A missing `done` means interruption, never success. Responses disable caching and proxy buffering. Reverse proxies must permit long-lived SSE connections. The browser Stop control aborts the fetch; ASGI cancellation closes the upstream provider stream and persists partial content as `interrupted`.

## Grounding and prompt boundaries

- All retrieval filters by authenticated organization **and** conversation chatbot, published document version and embedding model. PostgreSQL FORCE RLS is an independent barrier. New child-table composite foreign keys reject cross-tenant references.
- The prompt puts platform guardrails and tenant preferences in a system message. Escaped retrieved text and the visitor question remain user-role data. History is loaded from the database, never accepted from the browser. No tool execution is available.
- `CHAT_CONTEXT_MESSAGES` is a server ceiling; a request can lower it. Only complete user/assistant pairs are retained. The latest prior question is included in follow-up retrieval. This is bounded contextual retrieval, not a separate LLM query-rewriting pass.
- Prompt size uses a conservative UTF-8 byte bound with framing allowance. Older pairs, then lower-ranked passages, are removed to fit `CHAT_INPUT_TOKEN_BUDGET` and the model's context window. Oversized remaining input returns `context_limit` before any generation.
- No accepted passages means a deterministic fallback and no LLM call. Phase 5 always requires evidence, including when a bot's older `strict_grounding` setting is off. Nonempty retrieval is not a proof that a passage answers the question; model grounding still needs evaluation.
- Citation IDs are assigned to actual retrieved sources. Unknown numeric references are removed during streaming. Document links, titles and page numbers are taken from stored source metadata, never from model-authored URLs. Text is rendered as plain React text: no raw HTML, Markdown images or model-authored clickable links. Prompt boundaries reduce injection risk; they are not a guarantee that a real model will obey every guardrail.

## Usage, abuse controls and failure semantics

- Organization rate limit: 60 generation attempts/minute by default. Public sessions: 10/minute, 30 total attempts; public IP: 30/minute. Conversation creation/session issuance are also limited. Redis outages fail closed.
- An atomic Redis lease caps organization concurrency at 3 and prevents concurrent turns in one conversation. Leases have owner tokens and expire after a bounded failure window. A generation attempt has a total timeout (default 60s); the compatible transport retries connection failures and HTTP 429/502/503/504 before output, with bounded backoff. Partial streams are never retried.
- Monthly token and estimated-dollar limits are enforced before generation with a transaction-scoped organization advisory lock and a durable `chat_usage` reservation. Concurrent requests cannot spend the same remaining quota. Defaults are 2M tokens/$25 per UTC month; these are static operational caps until billing/entitlements ship.
- Reservations cover conservative input/output bounds for **all** possible attempts. Successful reported usage settles to provider token counts plus conservative prior retry allowances. With missing usage, cancellation, failure or process loss, uncertain usage remains conservatively charged. Estimated costs are not charges to a customer. Provider failures do not erase possible upstream spend.
- A hard process termination can leave a message marked `streaming` and a reservation `reserved`. Leases expire, but usage stays charged. Operators must reconcile such reservations with provider records; no automatic refund assumes that a request was free. Graceful disconnects are finalized and regression-tested.
- Message bodies are capped at 24KB before JSON parsing, questions at 4000 characters, context at a server-controlled budget and output at a transport ceiling as well as the provider's `max_tokens`. Quotas apply to playground and public traffic. Client retries create new turns and consume limits; there is no idempotent replay API in this phase.
- Content is intentionally persisted in the tenant database for conversation history, but generation code logs only message IDs and sanitized failure codes. It never logs prompts, retrieved passages, raw provider errors, bearer credentials or provider keys.

## Database and rollout

### AUD-01 stabilization (Milestone A1)

Chat authorization now produces a frozen scalar context and rolls back its read transaction
before service work. Session idle-touch releases the authentication checkout before using its
own short transaction. Chat-related authentication has a process-local gate (up to four
concurrent lookups, scaled down with a smaller pool), released before streaming. Ordinary CRUD
transaction semantics remain unchanged. Every new tenant transaction restores its RLS context.

Organization/conversation Redis admission precedes preparation. Admission waits at most
`CHAT_ADMISSION_WAIT_SECONDS` (default 0.9 seconds) before `429 chat_busy`. While it waits, a
release in the same API process wakes the oldest waiter at once. Polling is the fallback, for slots
freed by another process or by expiry: after 10, 20, 40, 80, 160 and then every 200 ms, with a last
attempt as the window closes (see the A6.1 stabilization report). Preparation has a
separate process-local ceiling, `CHAT_SETUP_CAPACITY` (default eight, scaled to pool capacity).
These ceilings are not a physical reservation of database connections. Actual checkout counts
and second-tenant availability must be measured; see the A1 implementation report.

Embedding runs without a checked-out database connection. The bounded local hash query executes
directly; compatible remote query embedding runs in a fresh, killable Python child using the
existing adapter. Credentials pass through stdin, not command arguments or logs. Timeout or
cancellation kills and reaps that child before releasing preparation capacity. No background
embedding thread is abandoned. The child also enforces its own hard wall deadline if the API
supervisor disappears. The existing embedding transport policy is unchanged (AUD-03
remains separate). Session/membership/permission or widget capability/domain/key state is checked
again after embedding and before reservation/generation. Public bootstrap creates its conversation
and token in one transaction; capability origin resolution reuses its current session.

`DB_POOL_TIMEOUT_SECONDS` defaults to two seconds (pool size five plus overflow five is unchanged).
Recognized pre-stream pool exhaustion returns sanitized `503 chat_unavailable` with Retry-After;
setup saturation also returns 503. Post-stream errors keep the existing SSE contract. Graceful
pre-stream interruption marks committed pending usage settled while retaining conservative
reserved charges; hard process loss still needs operational reconciliation. No schema migration
or new dependency is required for A1.
